# i18n — Malatro

Owner of the translation workflow and locale handling. Two independent systems carry text, and they
are not interchangeable — see below.

## Locales

- **Polish (`pl`) is the default in-game locale** — `DEFAULT_SETTINGS.locale = "pl"` and
  `<html lang="pl">` in `index.html`. [repo: src/lib/settings.ts]
- **English (`en`)** is a switch, available from the main menu (PL/EN buttons) and persisted in
  `malatro_settings_v1`. [repo: src/screens/MainMenu.tsx]
- Only these two locales exist (`LOCALES = ["pl", "en"]`, `src/lib/i18n.ts`).

## System 1 — Lingui (UI chrome strings)

Every user-facing UI string outside game *content* (buttons, labels, toasts, tooltips) is a Lingui
macro: `<Trans>...</Trans>` in JSX, `t\`...\`` from `useLingui()` elsewhere. `eslint-plugin-lingui`
fails lint on an unlocalized string in `src/components/**`/`src/screens/**` (the rule is off for
`src/lib/**`/`tests/**`, which carry bilingual data instead — see System 2).

- **English is the source locale** (`sourceLocale: "en"` in `lingui.config.ts`) and Lingui is
  configured so the **source string doubles as the message id** — there is no separate id scheme.
- Catalogs: `src/locales/{locale}/messages.po` (source, hand/script-edited) compiled to
  `messages.ts` (committed, imported by `src/lib/i18n.ts`).
- Compile is **strict** (`lingui compile --typescript --strict`): a missing translation for any
  extracted string **fails the build**, not just a runtime fallback.

### Workflow

```
bun run translate     # = lingui extract --clean && lingui compile --typescript --strict
```

In practice, extracting new English strings does **not** by itself produce Polish translations — the
freshly extracted `pl/messages.po` entries are empty. The actual fill step is a separate manual
script:

```
python scripts/translate-pl.py     # writes known English -> Polish pairs into src/locales/pl/messages.po
bunx lingui compile --typescript --strict   # (or `bun run i18n:compile`) re-compile after filling
```

`scripts/translate-pl.py` holds a hand-maintained `PL: dict[str, str]` mapping and **prints any
message id it doesn't have a translation for**, so a strict compile never silently ships an
untranslated English string as Polish. This script is not wired into `package.json`'s `translate`
script — running it is a manual step after `lingui extract`. [repo: scripts/translate-pl.py]

Tests stub the Lingui macro via the Bun preload (`tests/setup.ts`, per `bunfig.toml`) so `bun test`
doesn't need real catalogs. [research: context-analysis.md §10]

## System 2 — `L10n` (bilingual game content)

Game *content* — task summaries/topics, joker/boss/consumable/voucher/tag names and descriptions,
session names — is not run through Lingui at all. It is stored as an inline bilingual object:

```ts
type L10n = { pl: string; en: string };
```

read with `loc(text, locale)` (`src/lib/i18n.ts`) or the `l()` helper exposed by `SettingsContext`.
**Fallback direction differs from Lingui**: `loc()` falls back to `text.pl` if the requested locale's
string is falsy, whereas Lingui's own fallback is to English (`fallbackLocales.default: "en"`). In
practice both are always populated, so this only matters if new content is ever added with only one
language filled in. [repo: src/lib/i18n.ts]

This is why `eslint-plugin-lingui`'s unlocalized-string rule is disabled for `src/lib/**`: those
strings are legitimately hardcoded PL/EN pairs, not something Lingui should extract.

## Math terminology glossary

The Polish-math-to-English glossary used when writing `topic_en`/`summary_en`/`statement_en` for
task content lives in **`data-pipeline/ANNOTATE.md`** (ciąg arytmetyczny/geometryczny, wyraz,
dziedzina, zbiór wartości, miejsce zerowe, wierzchołek paraboli, pochodna, graniastosłup, ostrosłup,
etc. — about 30 terms). It is the single source of truth for math-content English wording; UI-chrome
translations (System 1) don't need it.

## House copy rule

**ASCII hyphen only**, never en/em dash, in every string in both systems — enforced for pipeline
content by `clean()`/`DASH_RE` in `data-pipeline/build_dataset.py`, and expected by convention for
hand-written Lingui strings (see `conventions.md`).
